## Release Note

This release adds two integration-facing capabilities — a lifecycle-aware global event bus and name-based serial coroutine execution — and upgrades Kotlin and kotlinx-coroutines. No source migration is required unless you adopt the new APIs, but projects with strict dependency version alignment requirements must review the new versions.

### New: `AppEvent` — Lifecycle-Aware Global Event Bus

A new in-process event bus is available under `com.bonepeople.android.widget.util.event`.

- **`AppEvent.register(owner, minState, action)`** — Binds a subscription to a `LifecycleOwner` (e.g. `Activity`, `Fragment`). The subscription is automatically cancelled on destroy; no manual unregister is required.
- **`AppEvent.post(event)`** — Posts an event from a coroutine context.
- **`AppEvent.postAsync(event)`** — Posts an event from a non-coroutine context (callbacks, click listeners, etc.) via `CoroutinesHolder.default`.

Define events by implementing the `AppEventData` marker interface. Prefer typed `data class` events for maintainability; use `CommonEvent(name, data)` for generic signal-only or payload-based events.

**Behavior highlights:**

- **Non-sticky delivery** — Subscribers do not receive events posted before registration. Events emitted while a subscriber is inactive (lifecycle below `minState`) are also not replayed on resume.
- **Lifecycle-gated receiving** — Posting is independent of subscriber lifecycle; receiving is gated by `minState` (default: `STARTED`).
- **In-process only** — Event objects are passed by reference within the same process.
- **Overflow policy** — Uses `DROP_OLDEST`; under extreme load, older buffered events may be dropped.

See [AppEvent documentation](../features/AppEvent/README.md) for usage examples.

### Enhanced: `CoroutinesHolder` — Name-Based Serial Execution

Three new APIs allow coroutine-level mutual exclusion by task name:

- **`runSerial(name, block)`** — Runs a suspend block serially within the caller's coroutine context.
- **`launchSerial(name, scope, context, start, block)`** — Launches a serial coroutine; defaults to `CoroutinesHolder.default` (`Dispatchers.Default`).
- **`asyncSerial(name, scope, context, start, block)`** — Same as `launchSerial`, but returns a `Deferred` for tasks with a result.

Tasks sharing the same `name` never run concurrently; tasks with different names are independent. `name` must not be blank.

**Important:** The underlying `Mutex` is not reentrant. Do not call `runSerial` with the same `name` from within a block already running under that name (including inside `launchSerial` / `asyncSerial`), or a deadlock will occur.

See [CoroutinesHolder documentation](../features/CoroutinesHolder/README.md) for details.

### Upgrade Recommendation

Recommended for projects that need lifecycle-safe cross-component event delivery or lightweight serial task coordination without introducing a separate EventBus library. No source migration is required for existing integrations. Projects that pin Kotlin or coroutine versions must ensure their constraints are compatible with Kotlin `1.9.25` and kotlinx-coroutines `1.8.1`.

## Upgrade Guide

This guide assumes the project is upgrading from 1.7.4 to 1.7.5. If the project is on an earlier version, apply the Upgrade Guides for each intervening release first.

### Required Actions

- [Required] Update the AndroidWidget dependency from `1.7.4` to `1.7.5`. For a direct JitPack declaration, search for `com.github.bonepeople:AndroidWidget:1.7.4` and replace it with:

```groovy
implementation 'com.github.bonepeople:AndroidWidget:1.7.5'
```

  If the version is managed by a version catalog, build property, or shared dependency constant, update that single source instead of each generated or resolved declaration.
- [Required if the project pins coroutine versions] Search build scripts, version catalogs, and dependency constraints for `org.jetbrains.kotlinx:kotlinx-coroutines-core`, `org.jetbrains.kotlinx:kotlinx-coroutines-android`, `kotlinx-coroutines-bom`, or the old version `1.6.4`. Update constraints that force these artifacts below `1.8.1`, or remove the constraint and allow AndroidWidget's exposed `1.8.1` dependencies to resolve. Do not replace unrelated `1.6.4` version strings.

No source, manifest, permission, ProGuard/R8, or initialization changes are required for existing integrations.

### Recommended Compatibility Checks

- [Recommended] Inspect the resolved application dependency graph and confirm that both `kotlinx-coroutines-core` and `kotlinx-coroutines-android` resolve to a compatible version, normally `1.8.1` or a deliberately selected newer version.
- [Recommended] Search Kotlin plugin declarations and version catalogs for `1.8.22` or an older Kotlin version. AndroidWidget 1.7.5 is built with Kotlin `1.9.25`; if the consumer build reports incompatible Kotlin metadata, update its Kotlin plugin to `1.9.25` or another version known to be compatible with the project's toolchain.

### Optional Adoption: Replace In-Process Event Boilerplate

- [Optional] Search for `LocalBroadcastManager`, app-local `sendBroadcast(` / `registerReceiver(` pairs, manually maintained global listener lists, or a custom global `LiveData` / `MutableSharedFlow` used only as a non-sticky event bus. When the events are in-process and may be discarded while a receiver is inactive, replace that plumbing with `com.bonepeople.android.widget.util.event.AppEvent`. Event types implement `com.bonepeople.android.widget.util.event.AppEventData`.

For example, a local broadcast such as:

```kotlin
LocalBroadcastManager.getInstance(context)
    .sendBroadcast(Intent(ACTION_REFRESH))
```

can become a typed event:

```kotlin
data class RefreshRequested(val source: String) : AppEventData

AppEvent.register(this) { event ->
    if (event is RefreshRequested) refresh(event.source)
}

AppEvent.postAsync(RefreshRequested("settings"))
```

`AppEvent.register` is lifecycle-bound, so remove manual unregister logic only for subscriptions that have actually moved to `AppEvent`. Do not replace system broadcasts, cross-process communication, sticky events, or events that must be replayed after an inactive lifecycle; `AppEvent` is in-process and non-sticky, and it does not replay events missed below `minState`.

### Optional Adoption: Replace Shared Serial-Execution Guards

- [Optional] Search coroutine code for shared `Mutex` / `withLock` guards, `ConcurrentHashMap<String, Mutex>` registries, or ad hoc "task running" flags whose only purpose is to prevent the same logical resource operation from running concurrently. When callers need to coordinate by a stable resource name, replace that boilerplate with `com.bonepeople.android.widget.CoroutinesHolder.runSerial`, `launchSerial`, or `asyncSerial`.

For an existing suspending call:

```kotlin
private val cacheMutex = Mutex()

suspend fun refreshCache() = cacheMutex.withLock {
    updateCache()
}
```

the shared named guard can be written as:

```kotlin
suspend fun refreshCache() = CoroutinesHolder.runSerial("cache") {
    updateCache()
}
```

Keep a local `Mutex` when its ownership is already clear and no cross-call-site coordination is needed. Named serial execution provides coroutine-level mutual exclusion, not thread confinement. Use a fixed name for each logical resource. The implementation keeps one `Mutex` per name for the process lifetime, so a dynamically constructed name retains its `Mutex` permanently. Choose an appropriate scope for `launchSerial` / `asyncSerial`. Do not call `runSerial` with the same name from inside a block that is already running under that name, including the block of `launchSerial` or `asyncSerial`. The underlying `Mutex` is not reentrant, so that nested call deadlocks immediately. Starting another same-name `launchSerial` or `asyncSerial` from inside the block does not by itself deadlock, but awaiting that nested job does.

### Verification

- [Recommended] Verify any adopted `AppEvent` subscriber receives events only while its lifecycle is at least `minState`, and confirm that missed-event replay is not required.
- [Recommended] Verify same-name serial tasks do not overlap, different-name tasks can still proceed independently, and no same-name serial call is nested.
- [Recommended] Verify the resolved coroutine dependencies and the application's existing coroutine behavior after dependency alignment.

## Changelog

- Added `AppEvent` lifecycle-aware global event bus with `register`, `post`, and `postAsync` APIs, backed by `MutableSharedFlow` with `DROP_OLDEST` overflow handling.
- Added `AppEventData` marker interface for typed event definitions.
- Added `CommonEvent` generic event type with `name` and optional `data` payload for signal-only or lightweight event scenarios.
- Added `CoroutinesHolder.runSerial`, `launchSerial`, and `asyncSerial` for name-based coroutine-level serial execution using a `ConcurrentHashMap` of `Mutex` instances.
- Documented non-reentrant deadlock risk when nesting same-name serial calls in `CoroutinesHolder` serial APIs.
- Upgraded Kotlin Gradle Plugin from 1.8.22 to 1.9.25.
- Upgraded kotlinx-coroutines-core and kotlinx-coroutines-android from 1.6.4 to 1.8.1.
- Added multilingual feature documentation for `AppEvent` (English, Chinese, Spanish).
- Updated `CoroutinesHolder` feature documentation with serial execution API usage and constraints.
- Restructured project and feature module documentation for consistent formatting and navigation across all supported languages.
- Added release note and changelog writing guidelines under `document/releases/`.
