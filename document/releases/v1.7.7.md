## Release Note

AndroidWidget 1.7.7 adds application foreground-state observation to `ActivityHolder` and a suspending Activity Result API to `IntentResult`. It also makes top-activity lookup and `Intent.launch()` safer during Activity transitions. Existing callback-based result handling remains available, and no source or configuration migration is required. However, top-activity selection now excludes finishing and destroyed Activities, so integrations that depend on receiving those instances or invoke Activity-dependent utilities during teardown should review the affected flows.

### New: Observe Application Foreground State

`ActivityHolder` now exposes the application's current foreground state through a synchronous property and a read-only `StateFlow`:

```kotlin
val isForeground = ActivityHolder.isAppInForeground

lifecycleScope.launch {
    ActivityHolder.appForegroundFlow.collect { isForeground ->
        updateForApplicationState(isForeground)
    }
}
```

`isAppInForeground` is `true` while at least one Activity is started. `appForegroundFlow` immediately emits its current value to new collectors and then emits foreground and background transitions. Its initial value is `false` until the first Activity starts.

Navigation between Activities and configuration changes do not produce an intermediate background state. This makes the API suitable for application-wide work that should react when the visible Activity set changes between active and inactive states. It does not indicate which Activity has input focus; use Activity-specific lifecycle or focus callbacks when that distinction matters.

See [ActivityHolder documentation](../features/ActivityHolder/README.md) for complete usage guidance.

### New: Await Activity Results in Coroutines

`IntentResult.await()` is an optional coroutine API for code that must suspend until the launched Activity returns. It then returns the same `IntentResult` for chained result processing:

```kotlin
Intent(this, DetailActivity::class.java)
    .launch()
    .await()
    .onSuccess { data -> showDetail(data) }
    .onFailure { result -> handleFailure(result.resultCode) }
```

The existing `onResult`, `onSuccess`, and `onFailure` callback APIs remain unchanged and can still be chained directly from `launch()` without `await()`. When `await()` is used, the result is already available before subsequent handlers run. Multiple coroutines may await one result. Cancelling a waiting coroutine does not cancel the launched Activity, so another coroutine or callback can still receive the eventual result.

`await()` resumes for every result, including cancellation and other non-`RESULT_OK` result codes. Chain `onSuccess`, `onFailure`, or `onResult` to handle the required outcome.

See [Activity Result documentation](../features/ActivityResult/README.md) for callback and coroutine examples.

### Changed: Safer Activity Resolution and Result Launches

`ActivityHolder.getTopActivity()` now skips Activities that are finishing or destroyed and returns the most recent remaining active Activity, or `null` when none is available. `Intent.launch()` uses that resolved host consistently, reducing launches against an Activity that is already leaving the screen.

If the underlying AndroidX launcher rejects a launch, `IntentLauncher` now clears the failed launch record and restores its capacity for a later attempt. Calls continue to throw when no eligible `ComponentActivity` is available or when the configured concurrent-launch capacity is exhausted. In 1.7.7, an `IntentLauncher` without a registered AndroidX launcher now also throws an explicit `IllegalStateException`; 1.7.6 silently returned an `IntentResult` and left that launcher capacity occupied.

### Compatibility

This release does not change the library's minimum, target, or compile SDK; Kotlin, Java, Android Gradle Plugin, or Gradle requirements; AndroidX or third-party dependency versions; library Manifest entries; consumer permissions or initialization requirements; data formats; or ProGuard/R8 rules.

The release is source-compatible but not behavior-identical for Activity resolution. `ActivityHolder.getTopActivity()` and library APIs that use it no longer select finishing or destroyed Activities. Calls made during Activity teardown may instead use an earlier active Activity, return without performing UI work, fall back to application resources, or report that no active Activity is available.

The sample application now requires Android 8.0 (API 26) and includes a redesigned startup experience, adaptive launcher icon, and icon-processing walkthrough. These sample-only changes do not raise the AndroidWidget library's minimum SDK, which remains API 23.

### Upgrade Recommendation

Upgrade to 1.7.7 to observe application foreground transitions without maintaining custom Activity counters, optionally await Activity results in coroutine code, and avoid selecting finishing Activities for global launches. No mandatory source migration is required, and the new APIs can be adopted incrementally. Integrations that call Activity-dependent APIs during navigation or teardown should complete the host-selection checks described for this release.

## Upgrade Guide

This guide assumes the project is upgrading from 1.7.6 to 1.7.7. If the project is on an earlier version, apply the Upgrade Guides for each intervening release first.

### Required Actions

- [Required] Update the AndroidWidget dependency from `1.7.6` to `1.7.7`. For a direct JitPack declaration, search for `com.github.bonepeople:AndroidWidget:1.7.6` and replace it with:

```groovy
implementation 'com.github.bonepeople:AndroidWidget:1.7.7'
```

  If the version is managed by a version catalog, build property, or shared dependency constant, update that single source instead of each generated or resolved declaration.

No source, Manifest, permission, initialization, dependency-alignment, data-migration, or ProGuard/R8 changes are required for existing integrations. The `IntentResult` callback APIs remain supported. Because top-activity selection has changed, the behavioral checks below still apply to integrations that can run Activity-dependent work during navigation or teardown.

### Recommended Checks

- [Recommended if the project calls `ActivityHolder.getTopActivity()` during Activity transitions] Search for `ActivityHolder.getTopActivity()` and verify code that runs while an Activity is finishing. The method now skips finishing and destroyed instances, so it may return an earlier active Activity or `null` instead of the most recently created Activity. Keep the new behavior for work that requires a usable Activity; pass an explicit Activity reference when an operation must target the finishing instance itself.
- [Recommended if the project launches Activities through `Intent.launch()` from global callbacks or background work] Search for the import `com.bonepeople.android.widget.activity.result.launch` and review its `.launch()` call sites. Confirm they run while an eligible `ComponentActivity` is active and handle `IllegalStateException` where the absence of an Activity is expected. Version 1.7.7 avoids finishing and destroyed hosts but does not queue a launch until a future Activity becomes available.
- [Recommended if the project invokes Activity-dependent utilities during navigation, teardown, or from a global callback] Search for `AppPermission.request(`, `AppKeyboard.hideKeyboard(`, `DateTimePicker.show(`, `DateTimePicker.showSystemDialog(`, and `AppDensity.getCurrentMetrics(`. When requestable permissions remain, `AppPermission.request()` now throws `IllegalStateException` with `No active Activity is available to request permissions` instead of using a finishing or destroyed Activity. When no eligible Activity exists, `AppKeyboard.hideKeyboard()` may return without hiding the keyboard and the `DateTimePicker` entry points may return without showing UI, while `AppDensity.getCurrentMetrics()` falls back to an earlier eligible Activity or application-resource metrics. Move UI work to an active Activity lifecycle when it must execute, and verify that the fallback behavior is acceptable for non-UI metric reads.

### Optional Adoption: Await Activity Results

- [Optional] Search call sites using `com.bonepeople.android.widget.activity.result.launch` for `.onResult {`, `.onSuccess {`, and `.onFailure {`. When subsequent coroutine logic must wait until the Activity returns, call `IntentResult.await()` after `launch()` before chaining the result handlers:

```kotlin
// Before
Intent(this, DetailActivity::class.java)
    .launch()
    .onSuccess { data -> showDetail(data) }
    .onFailure { result -> handleFailure(result.resultCode) }

// After
lifecycleScope.launch {
    Intent(this@HomeActivity, DetailActivity::class.java)
        .launch()
        .await()
        .onSuccess { data -> showDetail(data) }
        .onFailure { result -> handleFailure(result.resultCode) }
}
```

The callback APIs are not deprecated, so keep them when callback delivery better matches the surrounding code. Cancelling the coroutine waiting in `await()` does not cancel or finish the launched Activity. Do not treat coroutine cancellation as cancellation of the external Activity flow, and ensure another waiter or callback handles the eventual result when it must not be discarded.

### Optional Adoption: Replace Foreground-State Counters

- [Optional] Search for custom `Application.ActivityLifecycleCallbacks` implementations, started-Activity counters, or `ProcessLifecycleOwner` observers used only to expose a Boolean application foreground state. When the required meaning is “at least one Activity is started,” replace that plumbing with `ActivityHolder.isAppInForeground` for synchronous reads or `ActivityHolder.appForegroundFlow` for observation:

```kotlin
applicationScope.launch {
    ActivityHolder.appForegroundFlow.collect { isForeground ->
        if (isForeground) resumeApplicationWork() else pauseApplicationWork()
    }
}
```

Do not replace Activity-specific lifecycle or window-focus handling, because the global flow does not identify the current Activity or whether it has input focus. Review `ProcessLifecycleOwner` replacements carefully as well: its lifecycle timing is not identical to the started-Activity counting used by `ActivityHolder`.

### Verification

- [Recommended] Verify `ActivityHolder.appForegroundFlow` changes to `true` when the first Activity starts and to `false` after the last Activity stops, without emitting a temporary background state during Activity navigation or configuration changes.
- [Recommended] Verify adopted `IntentResult.await()` call sites chain the required result handlers and handle both `Activity.RESULT_OK` and non-success result codes, including user cancellation.
- [Recommended] If a coroutine awaiting a result can be cancelled, verify the application intentionally handles or discards the result that may arrive after cancellation.
- [Recommended] Verify global `Intent.launch()` call sites behave correctly when the latest Activity is finishing or when no eligible `ComponentActivity` is available.

## Changelog

- Added `ActivityHolder.isAppInForeground` for synchronous access to whether at least one application Activity is started.
- Added the read-only `ActivityHolder.appForegroundFlow` `StateFlow`, with an initial background value and foreground/background updates that avoid intermediate background transitions during Activity navigation and configuration changes.
- Added optional suspending `IntentResult.await()` to wait for the eventual Activity result and return the same chainable handler while supporting multiple waiters.
- Ensured an `IntentResult` completes its coroutine waiters after result callback dispatch, including when a registered callback throws.
- Updated `ActivityHolder.getTopActivity()` to ignore finishing and destroyed Activities and return the most recent remaining active instance.
- Applied the filtered top-activity selection to `AppPermission.request()`, `AppKeyboard.hideKeyboard()`, `AppDensity.getCurrentMetrics()`, and the `DateTimePicker` entry points, preventing those APIs from using finishing or destroyed Activities.
- Updated `Intent.launch()` to resolve its host Activity once and use the same host for launcher lookup and error reporting.
- Updated `IntentLauncher` to reject unregistered launchers explicitly and restore its launch record and capacity when the AndroidX launch call throws.
- Simplified coroutine-based `AppPermission.request()` to await its internal Activity Result directly while preserving the permission-status mapping for completed requests.
- Updated English, Chinese, and Spanish `ActivityHolder` and Activity Result documentation for foreground-state observation and coroutine result handling.
- Redesigned the sample application's startup screen, color palette, theme, and launcher artwork; added an adaptive icon and a screen documenting its image-processing steps; and raised the sample-only minimum SDK to API 26.
- Expanded the release-documentation guidelines and aligned or backfilled the version documents for AndroidWidget 1.7.0 through 1.7.6.
